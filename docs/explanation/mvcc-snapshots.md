# MVCC snapshots and recovery boundaries

NSNP v2 can transfer complete retained user MVCC chains, including tombstones,
pending puts/deletes and their physical transaction IDs. Readers accept v1 and
v2. Production writers use v1 by default and can enable v2 through the
[durable snapshot upgrade authority](upgrade-authority.md). Public shard migration
remains disabled.

## Writer eligibility and compatibility

`NodusRaftStore::with_snapshot_group` binds a snapshot to its Raft group.
`with_snapshot_compatibility` supplies a `SnapshotCompatibility` provider. The
provider must read trusted, durable finalization and capability evidence. V2 is
selected only when the finalized cluster version is at least 2 and every node
in the applied membership reports snapshot support at least 2. This includes
learners and both sides of joint membership. Missing or old reports retain v1;
provider errors fail the build. Empty membership cannot enable v2.

The server supplies the durable meta authority. Its leader verifies all members
using fresh capability challenges (peer mTLS for remote nodes) and persists
finalization through Raft. Meta membership freezes during and after activation;
production snapshot transport rechecks each v2 recipient before every chunk.
V2 readers do not require writer eligibility to decode. See the
[authority contract and rollout limits](upgrade-authority.md).

| State | Read | Write / rollback |
| --- | --- | --- |
| Earlier binary | Existing v1 | Cannot receive v2; old installer safety is not certified |
| New binary, no provider or gate off | v1 and v2 | Existing v1 bytes; refuses unrepresentable user state |
| New binary, verified finalized authority | v1 and v2 | v2; rollback to a v1-only snapshot reader unsupported |
| Existing storage-format reader | Existing SST/WAL/MANIFEST envelopes | Checkpoint adds a versioned local KV record, without changing those envelopes; older backup code does not enforce its recovery rules |

This is format and state-machine evidence using one binary, not a demonstrated
mixed-binary upgrade. Before finalization, v1 refusal remains an availability limit:
OpenRaft treats a build error for history, tombstones or intents as fatal.

## NSNP v2 layout and validation

Integers are unsigned big-endian. The layout is:

1. `NSNP`, followed by the two-byte version `2`.
2. An eight-byte length and JSON header containing the group, full Raft snapshot
   metadata (including membership and applied log ID), and catalog-presence flag.
3. An eight-byte row count. Each row contains an eight-byte key length, key bytes,
   and an eight-byte version count.
4. Each version contains its eight-byte timestamp and one-byte flags: bit 0
   indicates a value, bit 1 a transaction UUID, and bit 2 an intent. Optional UUID
   bytes (16) precede the optional eight-byte value length and value bytes.
5. A 32-byte SHA-256 checksum covering every preceding byte.

Rows have strictly increasing keys. Chains have strictly decreasing unique
timestamps, at most one intent, and no empty chains. An intent requires a UUID
and timestamp `u64::MAX`; committed versions cannot use that timestamp. Identical
duplicate storage versions are collapsed during export; conflicting timestamps
are rejected. Aborted empty chains are omitted. Unknown flags, excessive lengths,
trailing records, checksum errors, group/metadata mismatches, scope violations,
and invalid control records fail before the atomic storage replacement.

Latest catalog/control state must be committed and valid. The full durable
catalog blob, including authorization, remains authoritative; historical catalog
projections are not transferred as user history. Local Raft, clock and recovery
generation records are excluded. A receiving namespace preserves physical intent
IDs while translating row keys, so replicated commit/abort resolves those intents.

Wire and checkpoint accounting are capped at 128 MiB. The implementation holds
multiple buffers and pauses the shared engine; this is not a streaming installer.
Snapshot descriptor invalidation and atomic checkpoint publication retain the
[existing crash contract](../reference/durability-contract.md#atomic-raft-snapshot-installation).
Superseded files remain retained; crash tests assume an intact authoritative manifest.

## Backup recovery boundary

Every storage snapshot replacement atomically publishes a node-local generation
UUID and the new WAL's sequence floor with the data and applied pointer. The key
is `\0recovery\0generation`; its record is `NRBG`, a two-byte version `1`, a
16-byte UUID and an eight-byte big-endian WAL floor. Persistent reopen retains
the record; the memory engine uses floor zero. This identity is excluded from
Raft transfer and logical backup data and is regenerated by the receiving node.

The server binds `BackupOrchestrator` to its physical KV engine. Backup export
captures the generation before scanning and checks it again before sealing the
objects. A changed or unreadable identity rejects export. After a checkpoint,
the manifest includes the checksummed object `recovery-generation.v1.json`.
Existing manifest versions and pre-checkpoint backup bytes remain unchanged.

Backup creation, archival and PITR extension publish the observed boundary to
`recovery/current.v1.json` before proceeding. Both JSON records have explicit
version 1. Corrupt or unsupported records fail closed. Incremental creation
requires matching parent, export and current generation. Restore checks every
ancestry link, and PITR checks the base against the current generation both when
planning and before loading WAL. Indexed segments below the base's WAL floor
are excluded even if their timestamps overlap the requested range.

After installation, take a new full backup before further incremental/PITR use.
A historical full or same-generation incremental chain can still be restored;
an exact backup timestamp needs no WAL. Once a new generation is observed, PITR
extension from any older generation is conservatively rejected, even for a
target that predates the checkpoint. This avoids guessing across a WAL reset.

Repository publication is **not atomic with the storage checkpoint**. A detached
offline planner cannot discover a checkpoint until a source-bound operation has
published it. The repository must belong to one physical source; concurrent
uncoordinated sources sharing it are unsupported. A fresh source without the
repository's recorded history must use a separate repository. These checks do
not establish archive coverage beyond observed WAL or distributed backup retention.
An older binary ignores the new guard objects, so cross-version recovery is not
certified. Tests cover memory and filesystem repositories, persistent restore,
abrupt process exit, malformed records, ancestry mismatch and export/planning
races. S3 behavior, power loss, live-reader continuity and a linearizability proof
are outside this evidence.
